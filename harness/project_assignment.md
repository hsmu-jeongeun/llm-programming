# 개인 프로젝트 초기 하네스 구축하기

## 목표

개인의 프로젝트 제안서를 바탕으로 **AI와 함께 개발을 시작할 수 있는 프로젝트 초기 환경**을 구축한다.

프로젝트의 목적과 제약을 AI가 이해하고, 중요한 결정을 개인에게 확인하며, 작업 과정과 검증 결과를 문서로 남기도록 설계한다.

Codex 또는 Claude Code 하나를 선택한다. 

## 준비와 실행 방법

1. 자신의 프로젝트 폴더를 만들거나 기존 저장소의 별도 브랜치에서 시작한다.
2. 제안서 본문을 `proposal.md`로 저장한다. 
3. 해당 폴더에서 CLI를 실행한다. 
4. 아래 프롬프트를 **P1 → 개인 답변 → P2 → P3 → P4 → P5** 순서로 실행한다.
5. `[도구]`, `[나의 답변]`을 실제 내용으로 바꾼다. AI가 질문한 미정 사항은 개인이 결정한다.


| 단계  | 하는 일               | 주요 산출물                                |
| --- | ------------------ | ------------------------------------- |
| P1  | 제안서 분석·초기 결정       | 프로젝트 개요, 질문 목록                        |
| P2  | 프로젝트 규칙·의사결정·문서 체계 | AGENTS.md 또는 CLAUDE.md, workflow, ADR |
| P3  | 반복 업무용 스킬 작성       | 계획·검증·문서화 스킬 3개                       |
| P4  | 폴더·실행 환경·테스트 기반 구성 | 설정 파일, 환경 예시, smoke test, 테스트 계획      |
| P5  | 하네스 시험 운영·검토       | 스킬 실행 증거, 점검 보고서, 개인 회고               |


## P1. 제안서를 읽고 초기 환경에 필요한 결정 찾기

```text
나는 [도구: Codex 또는 Claude Code]를 사용한다.
proposal.md와 기존 프로젝트 파일이 있다면 그 구조를 읽어 줘.
목표는 이 프로젝트의 초기 개발 하네스를 구축하는 것이다. 앱 기능은 아직 구현하지 마.

제안서에서 다음을 찾아 docs/project-brief.md에 정리해 줘.
- 해결하려는 문제, 대상 사용자, 기대 결과
- 프로젝트 범위와 제외 범위
- 명시된 기술, 데이터, 외부 API, 실행 환경, 제약
- 데이터·키·개인정보 취급에 필요한 프로젝트별 주의사항
각 항목에 제안서의 근거 절/문장을 연결하고,
제안서에 명시된 사실 / 네 제안 / 미정 사항을 구분해 줘.
기존 파일을 읽어 실제 상태를 반영하고, 이미 구현됐다고 추측하지 마.

초기 환경 구성에 꼭 필요한 미정 사항을 docs/open-questions.md에 적어 줘.
개발 언어·도구, 데이터 사용, 유료 서비스 등 중요한 항목부터 질문을 최대 5개 제시해 줘.
각 질문은 선택지와 간단한 장단점, 추천 이유를 포함해 줘.
제안서에 이미 답이 있는 내용은 다시 묻지 마.
내 답변을 기다리고, 패키지 설치나 앱 코드 작성은 아직 하지 마.
```

**개인이 할 일:** 제안서 해석이 맞는지 확인하고 질문에 답한다. 확정할 수 없는 항목은 미정으로 남긴다. 예: “Python 사용, API는 나중에 연결, 개발 단계에서는 가상 데이터 사용”.

**산출물:** `docs/project-brief.md`, `docs/open-questions.md`.

## P2. 프로젝트 규칙·의사결정·문서 체계 만들기

```text
초기 결정에 대한 나의 답변은 다음과 같다.
[나의 답변]

proposal.md와 앞 단계 문서, 내 답변을 근거로 초기 하네스 문서를 실제 파일로 만들어 줘.
Codex이면 프로젝트 루트 AGENTS.md, Claude Code이면 CLAUDE.md를 사용해 줘.
이미 문서가 있으면 기존 내용과 충돌을 먼저 확인하고 필요한 부분만 보완해 줘.

1. 프로젝트 규칙 파일
- 목적과 범위, 확정한 기술/실행 환경
- 폴더별 역할과 수정 가능 범위
- 코딩·작업 원칙, 완료 시 검사·보고할 항목
- 중요한 결정은 언제 개인에게 질문하는지
- README, 프로젝트 개요, workflow, 테스트 계획, 결정 기록의 경로
자주 참고할 규칙만 간결하게 적고 상세 절차는 해당 문서에 연결해 줘.
아직 없는 실행·테스트 명령은 미구성으로 표시하고 성공했다고 쓰지 마.

2. docs/workflow.md
개인과 AI의 책임을 나누고 다음 흐름을 정의해 줘.
요청 확인 → 영향과 계획 정리 → 중요 결정 개인 확인 → 작업 → 검사 → 문서 갱신 → 개인 채택.
작성자와 검토자의 입력, 출력, 수정 범위를 적어 줘.
이번에는 한 CLI에서 역할을 순서대로 전환하고 개인이 흐름을 관리한다.
검사 실패 시 추가 수정은 최대 2회, 계속 실패하면 원인과 다음 조치를 적고 중단한다.
규칙 파일만으로 도구 권한이 강제되는 것은 아님을 명시해 줘.

3. docs/decisions/README.md와 결정 기록
개인 확인이 필요한 결정의 기준을 정해 줘.
예: 기술 스택 변경, 데이터/저장 방식 변경, 비용 발생, 외부 서비스 연결, 범위 변경.
확정한 중요한 초기 결정은 ADR(의사결정 기록) 파일로 남겨 줘.
형식: 상태(제안/확정/보류), 배경, 선택지, 선택과 이유, 영향, 결정자, 날짜.
사소한 파일 정리까지 모두 개인의 승인을 요구하지는 마.

4. README.md와 docs/testing.md 초안
README는 프로젝트 소개, 준비, 실행, 검사, 문서 탐색 경로를 담는다.
testing.md는 제안서에 맞는 테스트 대상과 전략을 담는다.
내용을 중복 복사하지 말고 문서별 기준 정보가 어디에 있는지 정해 줘.
README의 실행 명령은 P4에서 실제 확인한 뒤 완성한다고 표시해 줘.
앱 기능은 구현하지 마. 생성한 파일과 아직 미정인 항목을 요약해 줘.
```

**확인 질문:** AI가 자율적으로 처리해도 되는 일과 개인이 결정해야 하는 일은 무엇인가? 그 기준이 문서에 적혀 있는가?

**산출물:** 선택한 규칙 파일, `docs/workflow.md`, `docs/decisions/`의 기준·기록, `README.md`, `docs/testing.md` 초안.

## P3. 계획·검증·문서화 스킬 만들기

```text
제안서와 프로젝트 규칙, docs/ 문서를 읽고 이 프로젝트에 맞는 스킬 3개를 만들어 줘.
Codex이면 .agents/skills/<이름>/SKILL.md,
Claude Code이면 .claude/skills/<이름>/SKILL.md에 작성해 줘.
선택한 도구의 경로 하나만 사용하고, 기존 스킬이 있으면 중복 여부를 확인해 줘.
각 파일은 YAML의 name과 description, 본문의 입력·절차·산출물·중단 조건을 포함한다.
description에는 언제 쓰는지 명확히 적어 줘.

1. project-plan
새 요청을 받았을 때 제안서의 범위와 기존 결정을 확인하고,
영향 파일, 진행 순서, 검증 방법, 미정 사항을 workspace/plan.md로 정리한다.
중요한 결정이 필요하면 선택지와 근거를 제시하고 개인의 답변을 기다린다.
이 스킬은 앱 코드를 작성하거나 미정 결정을 확정하지 않는다.

2. project-check
프로젝트 환경이나 코드 변경 후 docs/testing.md에 따라 실제 검사를 실행한다.
workspace/checks.md에 명령, 종료 코드, 출력 요약, 필요 시 원본 로그 경로를 기록한다.
통과/실패/미실행을 구분하고, mock 검사와 실제 API 통합 검사도 구분한다.
앱 코드나 테스트를 고치거나 기준을 낮추지 않는다.
테스트가 0개이거나 아직 설정되지 않았으면 준비 부족으로 보고한다.

3. project-docs
작업 또는 의사결정 뒤 실제 변경과 기록을 읽고 관련 문서를 갱신한다.
README의 실행법, 프로젝트 개요, 테스트 계획, 결정 기록 중 무엇을 바꿀지 판단한다.
새로운 중요한 결정이 미확정이면 ADR 초안으로 남기고 개인 확인을 요청한다.
workspace/docs-update.md에 갱신 파일·이유·남은 질문을 적는다.
실행하지 않은 검사, 구현되지 않은 기능, 개인이 하지 않은 결정을 만들어 쓰지 않는다.

각 스킬의 내용을 내 프로젝트의 실제 폴더와 문서에 연결해 줘.
P4 전이라 명령이 미정이면 docs/testing.md를 참조하도록 하고 임의의 명령을 만들지 마.
스킬을 만들었다는 사실과 실제 호출에 성공했다는 사실은 구분해서 보고해 줘.
```

**산출물:** 프로젝트 전용 스킬 3개.  각 스킬이 언제 필요한지 한 문장으로 설명할 수 있어야 한다.

## P4. 초기 폴더·개발 환경·테스트 기반 구성하기

```text
확정한 프로젝트 개요·결정 기록과 규칙에 맞춰 개발을 시작할 최소 환경을 구성해 줘.
이번에는 앱 기능을 구현하지 않고 개발 기반과 검증 체계만 만든다.
기존 프로젝트라면 이미 쓰는 구조와 패키지 관리 방식을 유지해 줘.

- 기술 스택에 맞는 소스, 테스트, 문서, 작업 기록 폴더를 준비한다.
- 필요한 최소 의존성/설정 파일과 .gitignore를 작성한다.
- 환경 변수가 필요하면 값이 비어 있거나 가짜 값인 .env.example을 작성한다.
  실제 키는 읽어 출력하거나 저장소에 넣지 않는다.
- 의존성 설치가 필요하면 프로젝트 전용 가상환경/로컬 범위에 구성한다.
  전역 설정 변경, 유료 서비스 연결, 배포는 하지 않는다.
  환경 정책상 승인이나 개인 선택이 필요하면 필요한 항목을 설명하고 기다린다.
- 최소 smoke test를 작성하고 실제 실행한다.
  확정한 언어/도구에 맞춰 테스트 실행기가 동작하고 프로젝트 모듈/설정을
  로드할 수 있는지 확인하는 검사로 만든다. 무조건 참인 테스트로 채우지 않는다.
  검사에 필요한 최소 패키지 진입점/설정 로더는 만들 수 있지만 앱 기능은 구현하지 않는다.

실제 환경에 맞춰 docs/testing.md를 완성해 줘.
1. 지금 실행 가능한 초기 환경 검사와 명령, 기대 결과
2. 개발하며 추가할 단위/통합 테스트의 대상과 기준
3. 제안서에서 도출한 정상·경계·실패 시나리오 각각 1개 이상
4. LLM 출력/검색/외부 API가 있다면 그 특성에 맞는 평가 방법
   (해당하지 않는 항목은 불필요하다고 적기)
5. 외부 키 없이 실행하는 검사와 실제 연결이 필요한 검사의 구분

아직 구현되지 않은 기능의 테스트는 계획으로 표시한다.
초기 환경 검사 통과를 앱 기능 완성이나 품질 검증 완료로 표현하지 마.
실제 실행한 명령과 결과를 workspace/bootstrap-log.md에 기록하고
README에 재현 가능한 준비·검사 명령을 반영해 줘.
실행하지 못했으면 이유와 해결 방법을 기록해 줘.
```

**산출물:** 프로젝트에 맞는 폴더·설정 파일, 필요한 경우 `.env.example`, 실행 가능한 초기 검사, 구체적인 테스트 계획, 초기 구성 로그.

**확인 질문:** 새 개발자가 README만 보고 준비와 검사를 재현할 수 있는가? 지금 검증한 것과 앞으로 검증할 것이 구분되어 있는가?

## P5. 하네스 시험 운영과 최종 검토

CLI를 같은 프로젝트 폴더에서 다시 시작하고 선택한 도구로 스킬을 호출한다. 아래 호출은 셸이 아니라 **CLI 대화창**에 입력한다.

### 5-1. 계획과 의사결정 흐름 시험하기

Codex:

```text
$project-plan 제안서에 있는 다음 개발 작업 하나의 계획만 작성해 줘. 앱 코드는 구현하지 마. 범위, 필요한 결정, 예상 문서 갱신과 테스트를 제시해 줘.
```

Claude Code:

```text
/project-plan 제안서에 있는 다음 개발 작업 하나의 계획만 작성해 줘. 앱 코드는 구현하지 마. 범위, 필요한 결정, 예상 문서 갱신과 테스트를 제시해 줘.
```

개인은 질문이 있으면 답하고, 해당 결정의 상태를 기록하게 한다. 추가 결정이 없다면 없다고 기록한다. ADR 개수를 늘리려고 가상의 결정을 만들지 않는다.

### 5-2. 초기 환경 검사와 문서 갱신 실행하기

각 명령을 따로 실행하고 결과를 확인한다.


| 작업                 | Codex            | Claude Code      |
| ------------------ | ---------------- | ---------------- |
| 실제 초기 환경 검사        | `$project-check` | `/project-check` |
| 초기 구성 결과에 맞춰 문서 갱신 | `$project-docs`  | `/project-docs`  |


스킬을 찾지 못하면 경로·YAML을 확인하고 재시작한다. 직접 SKILL.md를 읽어 수행했다면 **파일 직접 읽기 수행, 스킬 발견 미확인**으로 기록한다.

### 5-3. 최종 검토 프롬프트

```text
이제 검토자 역할로 프로젝트 초기 하네스를 점검해 줘.
이번 과제의 목표는 기능 구현이 아니라 제안서에 맞춘 개발 초기 환경 구축이다.
앱 코드를 새로 구현하거나 검사를 성공시키려고 기준을 변경하지 마.

proposal.md, 규칙 파일, docs/, 스킬 3개, 초기 환경 파일, tests/, workspace/를 확인해 줘.
다음을 충족/미충족/미확인과 근거 경로로 workspace/harness-review.md에 정리해 줘.
- 목적·범위·기술·제약이 제안서 및 개인 결정과 일치하는가?
- 규칙, 스킬, 흐름 문서의 책임과 경로가 서로 맞는가?
- 중요한 결정의 개인 확인과 ADR 기록 방법이 있는가?
- 문서별 역할과 갱신 시점이 분명한가?
- README의 준비·검사 명령이 실제 환경과 일치하는가?
- 초기 smoke test 실행 증거가 있고 향후 기능 테스트 계획과 구분되는가?
- 스킬을 실제 사용한 기록이 있는가? 단순 파일 생성과 호출 성공을 구분했는가?
- 실패/미정 항목과 다음 행동을 남겼는가?

최종 상태를 준비 완료/보완 필요/판정 불가 중 하나로 적어 줘.
'준비 완료'는 초기 개발 환경 기준이며 앱이 완성됐다는 뜻이 아님을 명시해 줘.
문제가 있으면 구체적인 보완 항목을 적고 멈춰 줘.
```

## 체크리스트


| 생성된 항목                              | 확인할 내용                         |
| ----------------------------------- | ------------------------------ |
| proposal.md + docs/project-brief.md | 제안서 해석, 범위, 프로젝트별 제약           |
| AGENTS.md 또는 CLAUDE.md              | 지속적인 규칙·수정 범위·중요 결정 기준         |
| docs/workflow.md + docs/decisions/  | 개인/AI 책임, 재시도·중단, 실제 초기 결정     |
| 스킬 3개                               | 계획·검증·문서화의 반복 절차와 프로젝트 적합성     |
| README + 환경/설정 파일                   | 다른 사람이 초기 환경을 재현할 수 있는가        |
| tests/ + docs/testing.md            | 실행 가능한 초기 검사와 향후 테스트 전략        |
| workspace/ 기록                       | 초기 구성, 계획, 검사, 문서 갱신, 최종 리뷰 증거 |


아래 다섯가지 질문을 가지고 하네스를 점검한다.

1. 내 제안서 때문에 달라진 규칙이나 스킬은 무엇인가?
2. 내가 내린 중요한 초기 결정 하나와 그 이유는 무엇인가?
3. AI가 결정하면 안 되는 일은 무엇이며 언제 질문하게 했는가?
4. 지금 검증한 환경과 아직 검증하지 않은 기능은 무엇인가?
5. 다음 개발 요청을 받으면 이 하네스가 어떤 순서로 사용되는가?
